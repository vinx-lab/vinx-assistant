# 0001 微信收集箱第一期

显示名「Vinx 助手」，英文标识 `vinx-assistant`。

## 问题

平时在各种 App 上看到的内容（GitHub 项目、文章、短视频分享、截图）、路上想到的点子、个人待办（如发票报销），当时没空处理，需要先收下来，有空再逐条看。

现在的做法是发给微信「文件传输助手」，但收下来以后还得自己整理，时间一长就堆成一团，待办也容易忘。用过的笔记软件都不顺手。

目标：

- 在微信里发给一个 Bot，就算收下了。
- 后台定时自动归类、打标签、写摘要，提取截止时间。
- 待办要闭环：到期在微信里提醒，回复一句话就能标完成。
- 有空时在网页上逐条看待研究队列。
- 只有一个人使用。

## 范围

第一期要做：

- 通过微信 ClawBot（iLink Bot 协议）收消息：文字、图片、语音、文件、视频。
- 分类、标签、处理深度的识别，支持手动前缀和关键词。
- 定时 AI 批次，按处理深度分档，有每日 token 上限。
- 提醒：每日摘要，加上按截止时刻的逐条提醒；发不出去时等下次收件再补发。
- 在微信里用固定格式指令操作待办，固定格式解析不了时交给 AI 翻译。
- 网页：看板、详情、搜索、设置、用量，以及网页扫码登录。
- 单个二进制、单进程，可以在本机和服务器之间迁移。

第一期不做（第二期再评估）：

- Bot 自动回答问题，即「AI 自动回复」。
- 深度研究时联网搜索。
- 连续发的几条消息合并成一个条目。
- ntfy 等其他推送渠道。只预留接口。
- 网页访问控制（密码、来源 IP 白名单）。

## 已验证的事实（探针，2026-10-01）

用自写的 Python 探针，不依赖 OpenClaw，对照 iLink 协议实测了真实微信：

| 项 | 结果 |
|---|---|
| 扫码登录、长轮询收消息 | 可用，不需要公网地址 |
| 文字 | 可用；回执 `sendmessage` 返回 `ret=0` |
| 语音 | 可用；消息里自带微信的转写文字（`voice_item.text`），原始音频是 SILK 格式 |
| 文件 | 可用；文件名完整，MD5 与消息里的 `md5` 一致 |
| 图片 | 只能拿到压缩图（约 810×1440）。勾选「原图」后 `hd_size` 有值，但消息里只有一个下载地址，拿不到原图 |
| 其他 App 复制链接后粘贴 | 可用；收到完整的分享文本（标题加短链） |
| 长按消息转发给 Bot | 不行：转发列表里没有这个 Bot。已接受，入口改为打开 Bot 对话框直接发 |

已知的协议限制（来自上游仓库 Tencent/openclaw-weixin 的 issue）：

- 发消息要带上最近一条入站消息的 `context_token`。用户约 15 小时没给 Bot 发消息后，这个 token 会失效，Bot 主动发的消息会被拒（`ret=-2`）。Bot 自己发的消息不会续期 token（#309、#202）。
- `sendmessage` 有频率和累计额度限制，短时间内连发几条就会被持续限流（#270）。
- 协议里没有链接卡片、合并聊天记录这类消息类型（#86）。
- 请求头 `iLink-App-Id` 沿用官方插件的值 `bot`。独立客户端能否接入，官方没有答复（#265），这是合规风险，需要持续关注。

## 方案

### 架构

单个 Go 二进制，单个进程。业务按 `internal/` 下的包拆分：

| 包 | 职责 |
|---|---|
| `ilink` | 微信 iLink 协议：二维码登录、长轮询 `getupdates`、`sendmessage`、CDN 下载与 AES-128-ECB 解密。不含业务逻辑 |
| `ingest` | 收件：去重、解析前缀和关键词、识别指令、入库、保存附件、发回执（顺带补发积压的提醒） |
| `enrich` | 不调用 AI 的轻处理：提取 URL，抓取网页标题和简介 |
| `command` | 微信指令：用固定格式解析，解析不了再交给 AI 翻译，然后执行和撤销 |
| `store` | SQLite 表结构、迁移和读写。其他包只通过它访问数据 |
| `llm` | OpenAI 兼容接口客户端：`/v1/chat/completions`、`/v1/models`，统计用量 |
| `batch` | 定时 AI 整理：按处理深度分组、控制 token 上限、校验 JSON 并写回 |
| `remind` | 到期检查、每日摘要、补发队列 |
| `notify` | 推送渠道接口。第一期只实现微信 |
| `web` | 网页：页面、表单、扫码登录、设置。模板和静态资源用 `embed` 打包进二进制 |

子命令：

- `serve`：常驻运行，包含收件、定时任务和网页。
- `login`：在命令行扫码登录，作为网页登录的备用方式。
- `batch`：立刻跑一次 AI 整理。
- `backup`：在服务运行时导出 SQLite 快照，连同媒体目录一起打包。
- `version`：显示版本。

规则逻辑尽量写成纯函数，配上表驱动的单元测试，例如前缀和关键词解析、指令解析、提醒调度、token 预算。所有取当前时间的地方都改用可注入的时钟。时区固定为 `Asia/Shanghai`。

### 数据模型

**`items`**（条目）：一条微信消息对应一个条目，第一期不合并。

| 字段 | 说明 |
|---|---|
| `id`、`created_at` | 编号；收到消息的时间 |
| `msg_id` | 微信消息 ID，唯一，用于去重 |
| `raw_text` | 原文。语音存微信给的转写文字 |
| `url` | 从原文里提取的主链接 |
| `category` | `inbox`（未整理）/ `research`（待研究）/ `later`（稍后看）/ `todo`（待办）/ `idea`（点子）/ `archive`（资料） |
| `category_by` | 分类的来源：`prefix`（前缀）/ `ai` / `manual`（网页上手改） |
| `level` | 处理深度：`light`（轻量）/ `medium`（中等）/ `deep`（深度） |
| `status` | 状态，见下面的状态表 |
| `title`、`summary` | 标题；一句话摘要 |
| `detail` | 中等或深度处理产出的长摘要、研究笔记，Markdown 格式 |
| `priority` | 优先级：高 / 中 / 低 |
| `due_at`、`due_has_time` | 截止时间；是否带具体时刻 |
| `processed_level` | 已经按哪个深度处理过 |
| `process_error`、`process_attempts` | AI 处理失败的原因；已尝试的次数 |
| `tokens_used` | 这个条目累计消耗的 token |
| `raw_json` | 消息的原始 JSON，其中 `context_token` 已打码 |

**其他表**：

- `attachments`：附件，关联一个条目。字段有类型（图片 / 语音 / 文件 / 视频）、相对路径、原文件名、大小、MD5、下载状态（成功 / 待重试）。
- `tags`、`item_tags`：标签，以及条目和标签的多对多关系。
- `reminders`：提醒队列。字段有类型（`digest` 每日摘要 / `due` 到期提醒）、关联的条目、计划发送时间、状态（`pending` 待发 / `sent` 已发 / `deferred` 待补发 / `dropped` 已丢弃）、尝试次数、最后一次错误。
- `actions`：微信指令的执行记录，用于「撤销」。字段有指令、影响的条目、修改前后的值、时间。
- `llm_usage`：每次调用 AI 的记录，字段有日期、深度、模型、输入 token、输出 token、关联的条目。
- `settings`：网页上设置的配置，键值形式。服务商的 API 密钥也存在这里。
- `kv`：运行状态，比如 `getupdates` 的游标、最近一次 `context_token` 和它的时间、iLink 凭证。

**状态**：

| 分类 | 状态流转 |
|---|---|
| 待研究 | 待看 → 研究中 → 完成 / 放弃 |
| 稍后看 | 待看 → 已看 |
| 待办 | 待办 → 完成 |
| 点子、资料 | 存档。可以在网页上转成待研究或待办 |
| 未整理 | 等 AI 批次分类 |

全文检索用 SQLite FTS5，索引原文、标题、摘要、`detail` 和标签。迁移只新增、不修改已有迁移，文件放在 `internal/store/migrations/NNNN_名称.sql`。

### 收件流程（不调用 AI）

1. **去重**：`msg_id` 已经存在就跳过。游标在每轮 `getupdates` 后保存，重启后接着拉。
2. **识别指令**：消息以操作词开头（完成、搞定、推迟、改到、取消、删除、列表、撤销等，词表可在网页上配置），或者引用了 Bot 发的提醒消息，就交给 `command` 处理，不当作新条目。
3. **解析前缀和关键词**：
   - 分类关键词：消息中任何位置出现即确定分类（最早出现者优先，同位置取较长者），`category_by=prefix`；出现在开头且后面跟冒号、逗号或空格时，从正文中去掉，其余情况正文保持原文；不要求有分隔符才算命中。默认词表：待研究/研究、稍后看、待办/代办、点子/想法、资料；可在网页上配置。
   - 消息中出现的每个分类关键词都会给条目打上对应分类名的标签（可多个）；分类取最先出现的那个。
   - 关键词：带「研究一下」设为中等深度，带「深入研究」设为深度，都不带就是轻量。
   - 分类关键词表和深度关键词表都可以在网页上配置。
   - 没有前缀的条目先放进「未整理」。不过在图片开关关闭时，**没有前缀的图片直接归到「资料」**。
4. **入库并保存附件**：附件下载解密后存到 `media/年/月/`。下载失败时，条目照样保存，附件标记为待重试，由后台继续重试。
5. **回执**：回一条简短确认，比如「✓ 已收：待办｜…」。30 秒内连续收到多条时，只回一次「已收 N 条」。如果有待补发的提醒，就附在这条回执里一起发出。
6. **轻处理**：异步执行，不阻塞收件。提取 URL，抓取网页的 `<title>` 和 `og:description`，设超时，失败就跳过。

### 微信指令

- **固定格式**：`完成 12`、`推迟 15 明天`、`改到 15 10-08 15:00`、`取消 12`、`列表`、`撤销`。编号就是条目 `id`，前面的 `#` 写不写都行。固定格式由程序直接解析执行，不调用 AI。
- **固定格式解析不了时**：已经判断出是指令，但格式对不上，就立刻调用一次 AI，用轻量那档的模型。提示词里带上当前未完成的待办列表，只让 AI 把这句话翻译成一条标准指令（JSON）。程序只执行这条标准指令，而且只能操作已经存在的待办。
- **AI 也拿不准时**：返回候选项，让用户确认，比如「是指 #12 …还是 #15 …？」，不自行猜测。
- **执行后**：每条指令都回显执行结果，并写进 `actions`。`撤销` 会回滚最近一次指令。

### AI 批次

- **何时运行**：按时间表定时运行，默认每天 08:00 和 20:00，可以在网页上改。网页上的「立即整理」按钮和 `batch` 子命令可以手动触发。
- **处理哪些条目**：分类为 `inbox` 的，或者 `processed_level` 低于 `level` 的，按时间先后处理。
- **三档深度**：

| 深度 | 怎么调用 | 输出 |
|---|---|---|
| 轻量 | 10 到 20 条打包成一次请求，共用一份提示词 | 分类、标签、标题、一句话摘要、截止时间、优先级 |
| 中等 | 每条单独请求。先抓正文：GitHub 链接取 README，其他网页提取正文，截断到上限 | 再加上 3 到 5 句的摘要，说明值不值得看 |
| 深度 | 每条单独请求，正文上限更大 | 一份研究笔记：是什么、同类对比（只基于模型已有的知识）、上手步骤 |

- **结构化输出**：AI 只返回 JSON，程序做校验。格式不对就重试一次；还不行就写 `process_error`，下一批次再试，最多 3 次。
- **标签复用**：提示词里带上现有的标签列表，要求 AI 优先复用。
- **相对时间**：提示词里带上当前日期和时区，让 AI 把「月底前」「下周三」这类说法换算成具体日期。
- **分类优先级**：手动设的分类（`prefix` 或 `manual`），AI 不会改，只补充标签和摘要。
- **图片**：交不交给 AI 看由一个开关控制，**默认关闭**。打开后，图片会用低清晰度模式发给支持看图的模型。
- **token 上限**：每天的上限可以在网页上设。调用前估算，调用后按接口返回的 `usage` 累计。达到上限后，剩下的条目留到下一批次，网页上会显示有多少条在排队。

### 模型配置

- 在网页上可以添加多个服务商，每个填名称、API 地址、密钥。添加后调用 `/v1/models` 拉取模型列表，从下拉框选择。
- 轻量、中等、深度三档**分别选择**服务商和模型。
- 密钥只存在数据库里，网页上只显示后 4 位，日志里一律打码。
- 只依赖 OpenAI 兼容接口，不引入任何厂商的 SDK。

### 提醒

- **每日摘要**：默认每天 09:00 发一条，时间可以改。内容包括今天到期、明天到期、已逾期的待办，待研究积压的条数以及优先级最高的 3 条，昨天新收的条数。逾期的待办每天都会列出，直到完成为止，不另外单独催。
- **逐条提醒**：截止时间带具体时刻的，到点单独推送一条。只有日期的，不单独推送，只出现在当天和前一天的摘要里。同一个 10 分钟窗口内到期的几条合并成一条消息。
- **怎么发**：通过 `notify` 接口。微信渠道带上最近一次 `context_token` 去发：
  - 发送成功，标记为 `sent`。
  - 失败（如 `ret=-2`、被限流），标记为 `deferred`，不在原地重试。
  - 下次收到入站消息时，把 `deferred` 的提醒并进回执里发出。旧的每日摘要只保留最新一份，更早的标记为 `dropped`。
- 提醒消息里每条待办都带 `#编号`，方便直接回复指令。

### 网页

- **看板**：
  - 顶部状态栏：逾期和今天到期的待办数、微信连接状态（正常 / 需要重新扫码）、今天已用的 token、下次整理的时间，以及「立即整理」按钮。
  - 按分类分成标签页，每页显示条目数。
  - 条目卡片：标题、摘要、标签、链接、附件缩略图、优先级、截止时间；卡片上有状态按钮和「深入研究」按钮。
  - 可以按标签筛选。
- **详情**：原文、渲染后的 `detail`、附件（图片可直接查看，文件可下载，语音显示转写文字并提供原文件下载）。分类、标签、截止时间、优先级都可以手动修改。
- **搜索**：全文检索，可以按分类、状态、时间范围筛选。
- **设置**：服务商和模型、三档各用哪个模型、每日 token 上限、图片开关、整理时间、每日摘要时间、前缀表、关键词表、操作词表，以及微信扫码登录（页面上直接显示二维码）。
- **用量**：每天的 token 消耗、各条目的消耗、处理失败的条目和原因。
- **实现**：服务端用 `html/template` 渲染，交互只用少量原生 JS，全部打包进二进制。不引用任何外部 CDN 或字体，离线也能打开。手机上排版要正常。

### 运行与部署

- **启动参数**：只有三项，其余设置都在网页上改。

| 项 | 参数 / 环境变量 | 默认值 |
|---|---|---|
| 监听地址 | `--listen` / `VINX_LISTEN` | `0.0.0.0:3100` |
| 数据目录 | `--data` / `VINX_DATA` | `~/.local/share/vinx-assistant` |
| 代理 | 标准的 `HTTPS_PROXY` | 不设，即直连 |

- **数据目录**：`vinx-assistant.db`（SQLite，WAL 模式）和 `media/`。
- **访问控制**：第一期不设密码，也不限制来源 IP，靠部署环境的网络边界来保证安全。这是一个已知风险。
- **常驻运行**：用 systemd 单元，崩溃后自动重启，日志输出到 stdout，由 journald 收集。仓库里提供单元模板。
- **迁移到其他机器**：交叉编译出对应架构的二进制，拷贝二进制和数据目录，装上同一个单元即可。
- **构建**：`CGO_ENABLED=0`，SQLite 用纯 Go 实现。Go 环境由不入库的 `local.mk` 提供，Makefile 用 `-include local.mk` 引入。
- **日志**：一律对 API 密钥、`bot_token`、`context_token` 打码。

### 依赖

尽量只用标准库。预计需要的第三方依赖：

- `modernc.org/sqlite`：纯 Go 实现的 SQLite，支持 FTS5。
- 一个二维码生成库：用于网页扫码登录。
- 一个 HTML 解析库：用于抓网页标题和提取正文，可以考虑 `golang.org/x/net/html`。

## 取舍

- **入口选 ClawBot，没选企业微信「微信客服」**：微信客服支持转发、也能收链接卡片，但需要公网 HTTPS 回调，部署门槛不明。ClawBot 不用公网，本机就能跑，实测能满足主要的收件需求。代价是不能转发、收不到原图、主动推送受限，这几点都已接受。
- **不依赖 OpenClaw**：只需要 iLink 协议里的 7 个接口，自己实现更简单，部署也不必带上 OpenClaw 运行时。
- **选 Go 单二进制，没选 Python**：部署就是拷一个文件，常驻资源占用低。Python 已经写过探针，开发更快，但每次部署都要准备 venv 或 Docker。
- **单进程，没拆成多个进程**：只有一个用户，单进程最简单；状态集中在一个数据目录里，迁移和备份都方便。
- **没用 Markdown 文件当数据库**：改状态、按状态筛选、到期提醒都需要结构化查询。
- **AI 定时批量处理，不逐条实时处理**：省 token，也不用一直开着 AI 会话。唯一的例外是指令兜底，因为用户在等结果，所以实时调用。
- **提醒只走微信**：用户暂时不想用 ntfy。用「下次收件时补发」来弥补 `context_token` 失效的问题，代价是一整天不发消息时，提醒会延后。
- **一条消息就是一个条目**：自动合并容易合错，以后需要时，再通过加父条目字段来升级。

## 验证

- **单元测试**（表驱动）：前缀、关键词和操作词解析，固定格式指令解析，截止时间与提醒调度（注入时钟），token 预算，AES 解密，AI 返回 JSON 的校验。
- **假服务器链路测试**：用 `httptest` 模拟 iLink 后端和 OpenAI 兼容接口，覆盖下面这些场景：
  - 收件 → 入库 → 附件 → 回执；
  - 批次分类和打标签；
  - 每日摘要按时发送；
  - 发送被拒 → 标记待补发 → 下次收件时随回执补发；
  - 指令的固定格式执行，AI 兜底，撤销；
  - 异常情况：AI 返回坏 JSON、凭证失效（`-14`）、被限流、到达 token 上限。
- **构建不依赖全局环境**：在 `env -i HOME=$HOME PATH=/usr/bin:/bin GOENV=off GOPROXY=off` 下能编译通过。
- **真实微信验收**：
  1. 网页扫码登录；
  2. 发文字、图片、语音、文件和带前缀的待办；
  3. 手动触发一次整理，检查分类和摘要；
  4. 设一个几分钟后到期的待办，确认能收到提醒；
  5. 回复「完成 N」和一句自然语言的指令，再试「撤销」；
  6. 在手机浏览器上打开网页查看。
